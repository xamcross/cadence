# Phase 0 Research: Interviewer Feedback Forms & Reminder Escalation (F32)

All decisions verified against real source under `backend/src/main/java/com/cadence`. No `NEEDS CLARIFICATION` remained in the spec; this records the design choices and their grounding.

## D1 — One `feedbackRequests` collection: the request row IS the scorecard

**Decision**: A single `FeedbackRequest` (`@Document("feedbackRequests")`) holds both the ask (hashed token, TTL, reminder-escalation state, lifecycle status) and, on submission, the captured scorecard (an **encrypted `scorecardPayload`** JSON field + `submittedAt`). No separate `scorecards` collection.

**Rationale**:
- The F00.1-pre-created index `feedbackRequests {interviewEventId, submittedAt}` (`ChangeUnit001`, verified) is exactly a single-collection lookup: `submittedAt == null` ⇒ pending, non-null ⇒ submitted. A two-collection design would not use it.
- Keeps the PII surface to **one** encrypted field (`scorecardPayload`) that erasure clears with a single `$set null` — simpler than wiping across two collections.
- The spec explicitly allows either modelling (Key Entities: "may be the same persisted record … or a linked record — an implementation choice").

**Alternatives**: separate `scorecards` collection joined to `feedbackRequests` — rejected: a second collection, a second erasure target, and it doesn't use the pre-declared index. YAGNI (§I).

## D2 — "Interview occurred" detection = `SchedulingRequest` + one new `feedbackGeneratedAt` stamp

**Decision**: Generation is a scheduled scan of `SchedulingRequest` where `status == BOOKED AND feedbackGeneratedAt == null AND bookedStartAt <= now − generationDelay`, reusing the existing **`{status, bookedStartAt}`** index (`ChangeUnit014`/F23). For each match, a CAS `findAndModify({_id, status:BOOKED, feedbackGeneratedAt:null}, $set feedbackGeneratedAt=now)` fires generation exactly once; then one `FeedbackRequest` is fanned out per ACTIVE participant.

**Rationale**:
- `SchedulingRequest.bookedStartAt` is the denormalized interview start (set in the BOOKING→BOOKED CAS, F23, `SlotReservationService:298-306` — verified), the only queryable interview-time field. `status=BOOKED` is the live-booking marker; `CANCELLED`/`RESCHEDULED` are excluded by construction (FR-006 — a non-occurrence never matches).
- **`bookedEndAt` is NOT denormalized** (the end lives only inside the chosen `OfferedSlot` in memory). So the spec's "interview end + 24h" is anchored as `bookedStartAt + generationDelay` for the trigger and `+ submissionDeadline` for the first reminder — `generationDelay` (default `PT3H`) is a configurable post-interview offset that conservatively covers a typical interview length so a request is only created after the interview has plausibly ended. This is the honest grounding; it is documented in `FeedbackProperties`.
- `feedbackGeneratedAt` is one new nullable `Instant` on `SchedulingRequest`, exactly the F23 stamp pattern (`confirmationRequestedAt`/`escalatedAt`/`noShowAt`), `@Field(write=NON_NULL)` so a null is omitted from BSON. The CAS makes generation idempotent across overlapping/replayed sweeps (the F23 stage-1 `confirmationRequestedAt:null` precedent).
- **Index honesty (review SHOULD-FIX)**: the `{status, bookedStartAt}` index covers the `status=BOOKED AND bookedStartAt<=cutoff` prefix; the third predicate `feedbackGeneratedAt == null` is an **in-memory residual filter** (exactly the F23 `confirmationRequestedAt=null` shape on that same index), bounded by `generationQueryLowerBound` (a window floor so the scan never ranges ancient bookings) + the `Pageable` cap. So the scan is *bounded*, not "fully index-backed on all three predicates" — the honest framing. (An optional `{status, bookedStartAt}` partial index over `{feedbackGeneratedAt:{$exists:false}}` could make it fully covered, but the bounded-residual approach matches the accepted F23 precedent and avoids a fourth index; deferred unless profiling shows it matters.)
- **Reschedule (FR-022)**: a reschedule forward-commit creates a NEW `SchedulingRequest` (new `id`, its own `bookedStartAt`, `feedbackGeneratedAt == null`) and flips the parent to `RESCHEDULED` (`SlotReservationService.forwardCommitParent:623-637` — verified). So the old occurrence keeps its submitted scorecards (FR-022 retention); the new occurrence generates fresh requests once it occurs. The "occurred-and-generated-then-rescheduled-away" edge (where the parent's PENDING requests would keep escalating) is **unreachable**: a generated occurrence has `bookedStartAt + generationDelay < now` (it is in the past), and F20 refuses rescheduling a past interview — so a generated/occurred booking cannot be rescheduled away. No special-casing needed; SC-022 covers the submitted-then-attempted-reschedule retention.

**Alternatives**: (a) a separate "interview completed" event/collection — rejected (new infra, §C2); (b) re-scanning all past BOOKED interviews every sweep without a stamp — rejected (unbounded re-work + no idempotency anchor); (c) denormalizing `bookedEndAt` — deferred (not needed; `generationDelay` is sufficient and avoids touching the booking CAS again).

## D3 — Participant snapshot = ACTIVE `InterviewSlotClaim` member ids

**Decision**: The interviewer set for an occurrence is `InterviewSlotClaimRepository.findByWorkspaceIdAndSchedulingRequestId(ws, reqId)` filtered to `ClaimStatus.ACTIVE`. **`SlotReservationService.participantsFromClaims:421-425` is `private`** (verified), so `FeedbackService` calls the **repository** directly (the reusable seam) rather than the private method — same query, no cross-service coupling.

**Rationale**: This is the authoritative bound-at-confirmation panel (FR-001 "participant snapshot"). A pool member bound at booking is an ACTIVE claim; a released claim (cancel/reschedule) is `RELEASED` and excluded — so a non-occurrence/changed panel does not produce spurious requests. `ManagedCalendarEvent` rows are an equivalent source but claims are the reservation truth and already have the finder.

## D4 — De-dup: unique `{interviewEventId, interviewerMemberId}` + insert-catch-DuplicateKey

**Decision**: `interviewEventId = SchedulingRequest.id` (= `bookingRef`). A unique index `{interviewEventId, interviewerMemberId}` makes a second request for the same `{occurrence, interviewer}` a `DuplicateKeyException` the generator treats as the idempotent no-op (the F22 `emailDispatches`/F31 `slaNudgeDrafts` insert-catch precedent). Combined with the `feedbackGeneratedAt` CAS (D2), generation is doubly idempotent.

**Rationale**: FR-003 demands an atomic uniqueness primitive, not a read-then-write. `interviewEventId` aligns with the pre-declared `{interviewEventId, submittedAt}` index so the recruiter read-by-interview is also index-backed.

## D5 — Write-only token + STATUS-before-TIME resolution

**Decision**: 256-bit `SecureTokens.newToken()` per request, stored only as `TokenHasher.hashToken` (HMAC) in `tokenHash` (`@Field(write=NON_NULL)`, unique **partial** `{$exists:true}` index — the F23 `confirmTokenHash` precedent, NOT sparse, to avoid the F01 present-as-null collision). The URL carries only the token. Resolution (`findByTokenHash`) is **STATUS-before-TIME** (the F23/F30 precedent): a request that is `INVALIDATED` / `SUBMITTED` / `UNCOLLECTIBLE` / unknown → the **byte-identical invalid/used** response; only a `PENDING` request past `expiresAt` → the distinct **"expired"** response (FR-018/FR-030). The token grants **write-only** access (load returns a blank form + an interview context label; **no submitted content**), and the only token-routed endpoints are GET-load + POST-submit (FR-017).

**Rationale**: A write-capable no-login token could inject candidate-assessment PII on a guess, so correctness rests on entropy + the single-use CAS, not the advisory rate limiter (FR-016). STATUS-before-TIME keeps the no-auth endpoint from being a state oracle ("this candidate was erased" / "this interview was cancelled") — the F23 confirm-precedence lesson. Write-only closes the peer-disclosure / read-oracle risk; the recruiter read is the only content path (D10).

## D6 — Interviewer mail rides the operational member-mail path (NOT candidate dispatch)

**Decision**: The request + reminder emails go to the **interviewer (a Member)** via `EmailSender.sendEmail(memberId, templateId, mergeFields)` → `SmtpEmailSender`'s closed dispatcher (the F13 `INTERVIEW_CONFIRMATION_ID` branch precedent, `SmtpEmailSender:83-96` — verified), resolving the member address via `members.findByIdOptional` and substituting with `OperationalEmailTemplates`'s `{key}` `String.replace` (`SmtpEmailSender.substitute:112-123`). F32 adds two operational templates (`FEEDBACK_REQUEST_ID`, `FEEDBACK_REMINDER_ID`) and two dispatcher branches; the per-recipient unique scorecard link rides `mergeFields.put("link", rawLink)`.

**Rationale**: The recipient is a workspace member, not a candidate — so the candidate consent/erasure email gate (`ContactPermissionGate`, `EmailDispatchService`) **does not and must not** apply (FR-004). The candidate-facing `EmailMessageType.FEEDBACK_REQUEST` + `MergeToken.FEEDBACK_LINK` exist in the codebase but resolve the recipient as a **candidate** (`EmailDispatchService` decrypts the candidate address) — wrong recipient — so F32 does **not** use that path. (Honest note: those two enum values were scaffolded speculatively and remain unused by F32; removing them would touch the F21 `@PostConstruct`/completeness machinery, so they are left in place, vestigial.) Reminder idempotency therefore lives on the `FeedbackRequest` record (D7), not the candidate-keyed `emailDispatches` outbox.

**Caveat carried forward (review SHOULD-FIX)**: this operational path does **not** have the F21 candidate-preview "missing-field warning" (it is `{key}` `String.replace`); FR-011 for these member emails is the operational render discipline (every `{key}` substituted; no raw placeholder transmitted) — verified (`SmtpEmailSender.substitute:112-123`) that `substitute` only replaces non-null values and **leaves an unsupplied `{key}` as a literal in the body**. So a forgotten `mergeFields.put("urgency", ...)` would ship a literal `{urgency}` to the interviewer. A test asserts every `{key}` in both new templates is supplied at every `sendEmail` call site (test surface).

**Member liveness (review SHOULD-FIX)**: the deactivated-interviewer skip uses `member.isActive()` (status == ACTIVE), NOT merely "found" — `members.findByIdOptional` returns a member regardless of status. Honest bound (FR-009/FR-014): a member deactivated *after* a request is generated keeps a live PENDING link until the next reminder sweep CASes it `PENDING→UNCOLLECTIBLE`; the link is not killed synchronously at `RoleService.guardedDeactivate` time (no hook added there for the MVP — the sweep-driven flip is the accepted best-effort bound, the F23/F31 style). A submit by a just-deactivated interviewer in that window is harmless (it records that member's scorecard; no PII exposure). This is documented rather than building a synchronous deactivation→feedback hook.

## D7 — Reminder escalation: concrete cadence + per-`{request, level}` CAS

**Decision**: On generation, `nextReminderDueAt = generatedAt + effectiveSubmissionDeadline`, `reminderLevelSent = 0`. The reminder stage finder is `findReminderDue(PENDING, now, Pageable)` = `{status:PENDING, nextReminderDueAt: {$lte: now}}` on the new `{status, nextReminderDueAt}` index. Each send is a per-level CAS `findAndModify({_id, status:PENDING, reminderLevelSent: L}, $set reminderLevelSent=L+1, lastReminderAt=now, nextReminderDueAt = (L+1 < maxReminders ? now + reminderInterval : null))` then `sendEmail(FEEDBACK_REMINDER_ID, {…, urgency:level})`. `nextReminderDueAt = null` at the last level stops the scan from re-selecting it. Submission/invalidation/uncollectible/TTL-expiry flip `status` off `PENDING`, also removing the row from the finder (FR-014).

Concrete documented default (`FeedbackProperties`, FR-012): `generationDelay = PT3H`, `submissionDeadline = PT24H` (first reminder at deadline), `reminderInterval = PT24H`, `maxReminders = 3` (L1/L2/L3 at deadline+0/+24/+48h). No reminder before the deadline (the initial `nextReminderDueAt` is the deadline).

**Rationale**: Member-mail has no outbox idempotency, so the per-`{request, level}` CAS is the single-winner guard (overlapping sweep / restart loser is `matchedCount==0` → no second send, SC-020). The `{status, nextReminderDueAt}` index keeps the scan bounded and index-backed. "Escalating urgency" is realised as a distinct `urgency`/level merge value (and reminder level in the row), so escalation order is machine-verifiable, not subjective tone (FR-012/SC-004). The injected `Clock` makes the deadline boundary + DST deterministic (FR-021/SC-016) — `Duration.ofHours/Days` against absolute `Instant`s, the F23/F31 pattern.

**Alternatives**: one reminder template re-sent N times — rejected (no machine-identifiable escalation level → SC-004 unverifiable). A candidate-outbox-style dispatch — rejected (member mail, no candidate id; the per-row CAS is sufficient and simpler).

## D8 — Erasure interaction + cycle-break

**Decision**: `CandidateErasureService.wipe`, after its winning guarded `updateFirst`, calls a narrow `FeedbackInvalidator.invalidateForCandidate(ws, candidateId)` (alongside the existing `supersedeLiveScheduling` and `slaDraftInvalidator.invalidateOpenDraft`, `CandidateErasureService:88-92` — verified). The invalidator wipes the scorecard content of **every** non-cleared `FeedbackRequest` for the candidate, not just pending ones (the review BLOCKER — a SUBMITTED row's `scorecardPayload` is candidate-assessment PII that MUST be erased under FR-023/SC-013; encryption with a retained workspace-wide key is not Art. 17 erasure): `updateMulti({…,status:PENDING}, $set status=INVALIDATED, $set scorecardPayload=null, $unset tokenHash)` **and** `updateMulti({…,status:SUBMITTED}, $set scorecardPayload=null, $unset tokenHash)`. `$set null` for the converter-managed `scorecardPayload` (the F30 rule: NEVER `$unset` — `ClassCastException`); `$unset tokenHash` (a plain hash, drops it from the partial index so the link 404s, FR-030). The SUBMITTED row keeps its status for the "who responded" trail; only its content is gone. Part of the single atomic wipe with no resurrection window: `supersedeLiveScheduling` already CASes the candidate's live bookings off `BOOKED`, so the generation finder cannot produce a new request; STATUS-before-TIME resolution makes any surviving token a byte-identical invalid/used.

**Cycle-break (precaution, the F31 lesson)**: `CandidateErasureService` depends on the narrow **`FeedbackInvalidator`** interface, not the concrete `FeedbackService` — the established pattern (`SlaDraftInvalidator` is the verified precedent). F32's `FeedbackService` does **not** transitively need `CandidateStatusService`/`ErasureRequestService` (its collaborators are `SchedulingRequestRepository`, `InterviewSlotClaimRepository`, `FeedbackRequestRepository`, `EmailSender`, `MemberService`, `WorkspaceConfigService`, `CandidateAuditService`, `TokenHasher`/`SecureTokens`, `Clock`), so the construction cycle that bit F31 is not present — but the narrow interface costs nothing and is the house style, so it is used (no `@Lazy` expected to be necessary; add it only if a `@SpringBootTest` reveals a cycle).

**Rationale**: Matches the F23/F31 honest bound (best-effort invalidation + the structural guarantee is the resolution discipline + the booking supersede). Scorecard content is the one PII field, wiped in the same operation (FR-023/FR-028/SC-013).

## D9 — Per-workspace settings (FR-013) — reuse the F23 `WorkspaceConfig` pattern

**Decision**: Add two nullable `Duration` fields to `WorkspaceConfig` — `feedbackSubmissionDeadline`, `feedbackReminderInterval` — exactly as F23 added `confirmationLeadTime`/`unconfirmedEscalationDeadline` (verified). They are set via the **existing** `PATCH /api/internal/workspace/settings` endpoint (Admin-gated, audited); `SettingsPatch` and `WorkspaceConfigResponse` gain the two fields **at the end** of their positional records (the F23 lesson: this breaks existing positional-constructor test call sites — fix them in the same task). `WorkspaceConfigService.updateSettings` hard-codes the two new fields and runs a cross-field validator on the **effective** values (`patch ?? current ?? global default`) so a single-field edit can't slip past `deadline > 0`, `interval > 0` (the F23 validator precedent). `maxReminders` and `generationDelay` stay global (`FeedbackProperties`) for the MVP — not per-workspace (FR-013 names the deadline + cadence; the max/offset are documented defaults).

**Rationale**: Zero new config collection; the per-workspace deadline/cadence is the F23-proven shape. The global default (`FeedbackProperties`) applies when unset (FR-013).

## D10 — RBAC + no-existence-oracle; HM read deferred to F51

**Decision**: `InterviewFeedbackController` is `@PreAuthorize("hasAnyRole('ADMIN','RECRUITER')")`, workspace-scoped (the interview/scorecard is resolved via `findByWorkspaceId…` → `RbacExceptions.ScopedNotFoundException` for a cross-workspace id → indistinguishable 404). A dedicated `FeedbackExceptionHandler` (`@Order(Ordered.HIGHEST_PRECEDENCE)`, `@RestControllerAdvice(assignableTypes={ScorecardTokenController, InterviewFeedbackController})`) renders the value-free envelope and **must itself `@ExceptionHandler(ScopedNotFoundException)`** emitting `{"error":"not_found"}` (the global `RbacExceptionHandler` adds a `"message"` → byte-divergent oracle — the F31 fix); its catch-all `@ExceptionHandler(RuntimeException)` (preview/submit 500-hardening) **must re-throw `AccessDeniedException`/`AuthenticationException`** so `@PreAuthorize` 403s don't become 500s (the F31 fix).

**HM read deferred to F51 (the resolved scope fork)**: the backlog grants HM scoped scorecard read, but there is **no candidate→requisition→assignment data path** in the codebase (verified: `Candidate` has no `requisitionId`; the requisition entity + HM assignments are F51), and no candidate-creation flow populates one — so HM "own candidates only" scoping cannot be delivered end-to-end (constitution §II no-stubs) without pulling F51 forward (§I YAGNI). Consistent with the F31 precedent (HM excluded from SLA actions for the same reason), MVP scorecard read is ADMIN/RECRUITER; HM/Interviewer/Read-only are denied (enforced, SC-010). When F51 builds the link, HM scoped read can be added.

**Rationale**: The F30/F31/F02 no-oracle precedent; SC-010/SC-011 assert the 5-role matrix + indistinguishable 404.

## D11 — Public no-login chain + the §IX gate

**Decision**: The token endpoints (`GET /api/feedback/{token}`, `POST /api/feedback/{token}`) join the existing `@Order(2)` `securityMatcher("/api/public/**","/api/candidate/**")` permitAll/STATELESS/CSRF-disabled chain by adding `/api/feedback/**` (verified chain at `SecurityConfig` `@Order(2)`). Rate-limited via `CandidateRateLimiter.tryAcquire(ip)` (hashed-IP keyed; the F13/F30 precedent) → 429. The public `RbacEndpointInventory` allow-list adds `/api/feedback/**` (the internal controller keeps `@PreAuthorize`, enforced by the inventory test).

**§IX gate APPLIES (unlike F31)**: the scorecard form is an **interviewer-facing no-login page** — a candidate-class public surface — so it is held to WCAG 2.2 AA (axe 0 violations) + mobile-first (≥44 px) + Lighthouse Performance ≥85, reusing the F14 `axe-core` Karma harness, the `_headers` CSP, the token-in-memory-only discipline, and the `@lhci/cli` stub (add a `/feedback?token=lighthouse-demo` canned blank-form state to `serve-with-stub.mjs`). The recruiter status panel on `/scheduling` is an internal authenticated screen → gates N/A (the F50/F51 precedent).

**Rationale**: Constitution §IX / DoD: "no login … all candidate-facing pages WCAG 2.2 AA, mobile-first." The interviewer scorecard is exactly such a page; F31 had no such page (internal only), so this is the one place F32 carries the full §IX gate.

## D12 — Mongock `ChangeUnit017` (order "017")

**Decision**: `ChangeUnit017_FeedbackIndexes` (order "017" off the highest **applied** "016" — verified latest is `ChangeUnit016_SlaNudgeIndexes`) creates on `feedbackRequests`: unique `{interviewEventId, interviewerMemberId}` (de-dup, D4); unique **partial** `{tokenHash}` `partialFilterExpression {tokenHash: {$exists:true}}` (token lookup, D5); `{status, nextReminderDueAt}` (reminder scan, D7). Native `createIndex` + targeted `dropIndex` rollback (never `dropIndexes()`). Pure-ASCII comments (the F30 NUL-byte/binary lesson). **No `schedulingRequests` index** (the generation scan reuses `{status, bookedStartAt}` from `ChangeUnit014`). The `{interviewEventId, submittedAt}` index is already created by `ChangeUnit001` — not recreated.

## D13 — Frontend: a new public scorecard page + a recruiter status panel

**Decision**: (a) NEW lazy standalone `scorecard-page.component.ts` at `/feedback?token=…` — public, no-login, mobile-first: a blank scorecard (recommendation radios + optional 1–4 rating inputs + optional comment), submit, and states loading/form/submitted/expired/invalid; token held in a memory-only field (never `localStorage`), re-resolved on init (the F14/F30 hardening). Held to axe 0 + Lighthouse ≥85. (b) MODIFIED `scheduling.component.ts` + a `.feedback-status-panel`: for an entered interview/candidate, per-interviewer submission status + read decrypted scorecards (internal screen — axe advisory). New `feedback.service.ts` (public) and `interview-feedback.service.ts` (internal), both on `apiBaseUrl`.

**Rationale**: The §II demonstrable leg needs the real no-login form browser→DB (the F13/F14 precedent) plus a recruiter read surface. There is no candidate/interview list view yet (manual id entry on `/scheduling`, the F31 precedent) — the richer board is F51.

## D14 — PII discipline

**Decision**: The only PII at rest is the **encrypted `scorecardPayload`** (free-text comment + structured response as JSON, converter-encrypted via `MongoPiiConfig` the F13 `locationText` way) and the hashed token. Logs use ids + `.name()` strings + value-free outcome reasons (never pass an enum to `StructuredArguments.kv` — the F01.1 logstash Jackson-3 `NoSuchFieldError` footgun). `DeadLetterService.recordFailure` receives a PII-free cause-class summary (`render_failed: <SimpleName>`), never a raw render/send exception that could carry scorecard or merge content (the F22 dead-letter footgun). The interviewer email address (member, converter-decrypted at send) and the candidate name are never logged. `ci.yml` PII scan extended with `SENTINELF32*` (scorecard free-text, recommendation, interviewer email, candidate name) driven through generate→send→submit→remind→read and asserted absent in logs, dead-letter, audit, and the persisted row (SC-014) — including a **forced render/send failure** asserting the dead-letter carries only the cause class.

**Rationale**: Scorecard content is personal data about the candidate (FR-028); one encrypted field + value-free logging + the dead-letter discipline is the F30/F31-proven shape.
