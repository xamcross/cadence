# Feature Specification: Interviewer Feedback Forms & Reminder Escalation

**Feature Branch**: `018-interviewer-feedback`  
**Created**: 2026-06-17  
**Status**: Draft  
**Input**: User description: "checkout main, update from origin. find next unimplemented feature from the backlog and create spec for it. review with subagents" (resolves to **F32 — Interviewer Feedback Forms & Reminder Escalation**, the next unimplemented feature in the backlog delivery sequence after F31)

## Overview

Missing interviewer feedback is the silent blocker behind most "still deciding" limbo: an interview happens, a decision waits on a scorecard that never gets filled in, and the candidate sits in silence. Cadence closes that loop. After each interview, the system asks every interviewer on the panel to complete a short, structured scorecard via a private no-login link; if an interviewer does not submit by the workspace's deadline, Cadence sends reminder emails of escalating urgency until they do. Recruiters (and Hiring Managers, for their own candidates) can see who has and has not responded and read submitted scorecards, so the feedback-to-decision gap becomes visible and chaseable instead of invisible and stuck.

This feature is within MVP scope (product spec §11 "feedback forms with reminders"; FR-13; backlog F32). Voice-to-scorecard capture is explicitly deferred to v1.5. It depends only on already-delivered capabilities: the booked-interview record and its panel participants (F13 scheduling, F10/F11 calendar events), the role model and server-side assignment scoping (F02), the workspace time zone and configurable settings (F03), the candidate record with its consent/erasure/audit state (F04), the email template library + merge renderer with missing-field warnings (F21), the member/operational mail path and in-app recruiter notification (F01/F22), the candidate-style private-token + rate-limiter + no-login security chain (F13/F14/F30), and the shared `@Scheduled` + `SchedulerCheckpoint` idempotency/missed-fire pattern (F00.2). The `feedbackRequests` collection index was pre-declared in F00.1.

> **Multi-role review applied (2026-06-17, two rounds, findings folded in)**: Business Analyst, Security/GDPR Lead, QA Lead, and Backend/DevOps Lead reviewed the draft against the real codebase. Load-bearing corrections now reflected below: (1) the scorecard request and its reminders are addressed to **interviewers (workspace members with known addresses)**, not candidates, so the candidate consent/erasure email gate does **not** gate them — but the scorecard **content is personal data about the candidate**, so erasure MUST wipe scorecards and pending requests, and scorecard free text MUST never be logged (FR-028/FR-029/FR-023). (2) The submission token is **write-only and bounded to two endpoints (load + submit)**: no token path may return submitted content (FR-017). (3) Token resolution is **STATUS-before-TIME**: an invalidated/erased/cancelled/superseded request collapses to the byte-identical invalid/used response, so the no-auth endpoint is never an oracle for "candidate erased" or "interview cancelled"; only a genuinely past-TTL-but-otherwise-valid request returns the distinct "expired" message (FR-030). (4) Feedback requests are generated only for interviews that **actually occurred** (start passed, not cancelled/rescheduled-away), from the **booked participant snapshot**; a reschedule/cancel invalidates a pending request (FR-001/FR-006/FR-022). (5) Reminder escalation has a **concrete documented cadence and bounded maximum**, idempotent and missed-fire-safe with a per-`{request, level}` atomic guard so a restart or overlapping fire cannot double-send (FR-012/FR-015). (6) The interviewer request/reminder emails ride the **operational member-mail path** (not the candidate template renderer), so the "missing-field warning" is the operational-template render discipline, not the F21 candidate-preview warning (FR-004/FR-011). (7) Scorecard content uses the **same encryption-at-rest mechanism as other candidate PII** and is cleared on erasure as part of the single atomic wipe with no resurrection window (FR-028/FR-023). (8) Scorecard read is **Admin/Recruiter only** for the MVP (Interviewer, Read-only, and Hiring Manager denied), with an indistinguishable not-found for out-of-workspace ids; HM scoped read is **deferred to F51** because no candidate→requisition→assignment data path exists yet to scope an HM on (FR-025/FR-026, US3 scope decision).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Interviewer submits a scorecard from an email link (Priority: P1)

After an interview takes place, each interviewer on the panel receives an email containing a private link to a lightweight scorecard for that specific interview and candidate. The interviewer opens it on web or mobile — no login, no app — records a structured recommendation and brief notes in under a couple of minutes, and submits. The feedback is captured against the interview and candidate.

**Why this priority**: This is the core capability — capturing structured feedback with the lowest possible friction is what unblocks the hiring decision. Without it, nothing else in the feature has anything to remind about or display. It is the smallest independently shippable slice that delivers value (an interviewer can give feedback) and is P1.

**Independent Test**: Generate a feedback request for a completed interview, follow the emailed link without authenticating, submit a scorecard, and confirm the scorecard is persisted and linked to the correct interview and candidate; confirm the form never required login or account creation.

**Acceptance Scenarios**:

1. **Given** an interview that has occurred with an assigned interviewer, **When** the system generates the feedback request, **Then** the interviewer receives an email with a private scorecard link addressed to that interviewer for that interview.
2. **Given** an interviewer opens their valid scorecard link, **When** the form loads, **Then** it presents a blank lightweight scorecard (recommendation + structured fields + optional notes) with no login prompt and no previously submitted content shown.
3. **Given** an interviewer completes the required fields, **When** they submit, **Then** the scorecard is recorded against exactly one `{interview occurrence, interviewer}` pair and a confirmation is shown.
4. **Given** an interviewer submits with a required field missing, **When** they submit, **Then** the submission is rejected with a clear, field-level validation message and nothing is persisted.
5. **Given** a panel of multiple interviewers, **When** requests are generated, **Then** each interviewer gets their own independent link and scorecard; one interviewer's submission does not complete or reveal another's.

---

### User Story 2 - Escalating reminders until feedback is submitted (Priority: P1)

If an interviewer has not submitted their scorecard by the workspace's configured deadline, Cadence sends reminder emails with escalating urgency until the feedback is submitted (or a stop condition is reached). The recruiter no longer has to manually chase interviewers.

**Why this priority**: The chasing is the differentiator — a one-shot request that is never followed up reproduces the exact problem this feature exists to solve. Reminder escalation is what actually moves feedback turnaround. It ships with Story 1 and is P1.

**Independent Test**: With an injected clock, advance time past the configured deadline for an unsubmitted request and confirm the scheduled task sends a reminder; advance further and confirm the next-level (more urgent) reminder; submit and confirm no further reminders are sent; verify a restart mid-cycle does not produce duplicate reminders.

**Acceptance Scenarios**:

1. **Given** an unsubmitted scorecard whose deadline has passed, **When** the scheduled reminder task runs, **Then** a reminder email is sent to the interviewer.
2. **Given** an interviewer remains unsubmitted after the first reminder, **When** the next escalation interval passes, **Then** a more urgent reminder is sent, up to a bounded maximum number of escalations.
3. **Given** an interviewer submits their scorecard, **When** the reminder task next runs, **Then** no further reminders are sent for that request.
4. **Given** the reminder task host restarts mid-cycle or a fire is missed, **When** the task next runs (or replays), **Then** outstanding reminders are sent without sending any reminder twice (idempotent, missed-fire-safe).
5. **Given** an Admin configures the workspace feedback deadline and escalation cadence, **When** the task evaluates requests, **Then** it uses the workspace-configured values (with a documented default when unset).
6. **Given** an interviewer has been deactivated or removed from the workspace, **When** the reminder task runs, **Then** no further reminders are sent to them and the recruiter is alerted that the feedback cannot be collected.

---

### User Story 3 - Recruiter sees who responded and reads scorecards (Priority: P2)

A recruiter can see, per interview, which interviewers have submitted feedback and which are still pending, and can read the submitted scorecards. This turns feedback status from an invisible blocker into a chaseable, visible signal.

**Why this priority**: Visibility makes the captured feedback actionable and exposes non-responders, but the capture (Story 1) and the automated chasing (Story 2) already deliver standalone value without a viewing surface. P2.

> **Scope decision (2026-06-17, plan review)**: The backlog's HM-scoped scorecard read (original US-F32-4) requires a candidate→requisition→assignment data path to scope a Hiring Manager to "their own candidates." That link **does not exist in the MVP codebase** (the candidate record has no requisition reference; the requisition entity and its HM assignments are F51 territory and unbuilt), and no candidate-creation flow populates one — so an HM read could not be delivered end-to-end (constitution §II no-stubs) without pulling F51 forward (§I YAGNI). Consistent with the F31 precedent (HM excluded from SLA actions for the same "no assignment model yet" reason), **MVP scorecard read is ADMIN + RECRUITER only; HM scorecard visibility is deferred to F51**, when the requisition↔candidate↔assignment link exists. The HM denial is enforced (not silently absent).

**Independent Test**: Submit scorecards for some interviewers on an interview and leave others pending; as a Recruiter, confirm the submitted scorecards are readable and the pending interviewers are listed; as a Hiring Manager, an Interviewer, and a Read-only user, confirm access is refused.

**Acceptance Scenarios**:

1. **Given** an interview with a mix of submitted and pending scorecards, **When** a Recruiter views it, **Then** they see each interviewer's submission status and can read the submitted scorecards' content.
2. **Given** an Interviewer, **When** they attempt to read another interviewer's scorecard, **Then** access is refused.
3. **Given** a Read-only user, **When** they attempt to read scorecards, **Then** access is refused.
4. **Given** a Hiring Manager (MVP — no candidate-scoping data path yet), **When** they attempt to read scorecards, **Then** access is refused (deferred to F51).
5. **Given** submitted and outstanding scorecards across interviews, **When** a Recruiter looks at the feedback-pending view, **Then** they see a per-interview / per-interviewer pending count they can act on.

### Edge Cases

- **Interview never happened**: An interview that was cancelled, or rescheduled to a future time, before it occurred MUST NOT generate a feedback request; if a request was already generated for a now-cancelled/rescheduled interview, that pending request is invalidated or deferred so an interviewer is not asked to score an interview that did not take place (FR-006/FR-022).
- **Expired token**: A scorecard link past its TTL returns a distinct "expired" response with a helpful, user-facing message (contact your recruiter), distinguishable from an invalid/used token, never a generic 404 or 500 (FR-018).
- **Used / re-visited token**: After submission, re-opening the link shows an "already submitted, thank you" state and MUST NOT redisplay the submitted content (write-only; FR-017).
- **Concurrent double-submit**: Two simultaneous submissions with the same token (double-tap, retry) result in exactly one persisted scorecard; the second is an idempotent no-op or a clear "already submitted" response, never a duplicate record (FR-019).
- **Candidate erased**: When the candidate is erased, all scorecards and any pending feedback requests for that candidate's interviews MUST be wiped/invalidated, no further reminders are sent, and an outstanding link no longer functions (FR-023).
- **Reschedule after submission**: If an interview is rescheduled after some feedback was already submitted, the existing submitted scorecards are retained against the original interview occurrence; the rescheduled (future) occurrence is treated as a new interview for feedback purposes once it occurs (FR-022).
- **Interviewer deactivated**: A deactivated/removed interviewer stops receiving reminders; the recruiter (or active Admin/Recruiter fallback) is alerted that feedback for that slot cannot be collected (FR-009).
- **No assignable recruiter / fallback**: Reminders are interviewer-addressed, so they do not depend on a recruiter; but the "cannot collect feedback" alert (deactivated interviewer) falls back to the workspace's active Admin/Recruiter members so it is never silently dropped (FR-009).
- **Rate-limited token endpoint**: Repeated requests to the public scorecard endpoint from one source are rate-limited; excess requests are throttled rather than served (FR-020).
- **Clock / time-zone correctness**: The deadline and escalation intervals are evaluated against the workspace time zone with an injectable clock, so a deadline near a DST change does not fire early/late or twice (FR-021).
- **Missing merge field in the email**: If a merge field for the request/reminder email is unavailable, it surfaces as a visible warning in template preview and never sends a raw unrendered placeholder to the interviewer (FR-011, reuses F21 behaviour).

## Requirements *(mandatory)*

### Functional Requirements

**Feedback request generation**

- **FR-001**: After an interview has occurred, the system MUST generate one feedback request per assigned interviewer for that interview, each request bound to exactly one `{interview occurrence, interviewer}` pair. The interviewer set MUST be the **participant snapshot recorded on the booked interview** (the participants bound at confirmation), so a post-booking pool/panel change does not retroactively create or cancel requests for the wrong members.
- **FR-002**: Each feedback request MUST be linked to the candidate and the interview event so submitted feedback can later be attributed and retrieved, and so erasure can find and wipe it (FR-023).
- **FR-003**: Feedback-request generation MUST be idempotent: the same interview occurrence and interviewer MUST NOT produce two requests (and therefore not two request emails), even across repeated or overlapping scheduled runs — enforced by an atomic uniqueness primitive over `{interview occurrence, interviewer}`, not a read-then-write.
- **FR-004**: On generation, the system MUST send the interviewer a request email containing their private scorecard link, rendered as **operational member mail** (the member-mail path, addressing the interviewer at their known member address) with the appropriate merge fields. Because the recipient is a workspace member (the interviewer), this email is **not** subject to the candidate email-consent/erasure gate; however, see FR-023 for the candidate-erasure interaction. (The candidate template library + candidate merge renderer is a distinct, candidate-facing path; these interviewer emails use the operational-template path.)
- **FR-005**: Feedback-request generation MUST run on the shared `@Scheduled` + `SchedulerCheckpoint` pattern (F00.2) under its own checkpoint name, OR be triggered at a deterministic point in an existing scheduled flow; either way it MUST be idempotent and missed-fire-safe and key its detection query on an index-backed field (the pre-declared `feedbackRequests {interviewEventId, submittedAt}` index, plus any interview-time index declared in `plan.md` per F00.1) — never a full-collection scan.
- **FR-006**: The system MUST only generate requests for interviews that actually took place: an interview that was cancelled before its start, or rescheduled to a future time, MUST NOT generate a feedback request for the non-occurrence.

**Scorecard form & submission (no login)**

- **FR-007**: An interviewer MUST be able to open their scorecard via the private link with no authentication, no account, and no app install, on mobile and desktop.
- **FR-008**: The scorecard form MUST capture a lightweight structured response using a single fixed MVP shape: a **required overall recommendation** on a defined four-point scale (Strong Yes / Yes / No / Strong No), an optional set of **structured competency ratings** (zero or more named dimensions each scored on a 1–4 scale), and an **optional free-text comment** (bounded maximum length). A submission is "valid" iff the required recommendation is present and every supplied rating is within range. Configurable per-stage scorecard templates and voice-to-scorecard capture are out of scope — see Assumptions.
- **FR-009**: If the assigned interviewer has been deactivated or removed from the workspace — discovered **either at request-generation time or at reminder time** — the system MUST stop attempting to collect their feedback, MUST invalidate any outstanding scorecard link for that interviewer (offboarding hygiene — a deactivated member's no-login write-link ceases to function, collapsing to the indistinguishable invalid/used response per FR-030), and MUST alert the workspace's active Admin/Recruiter members that feedback for that interview slot cannot be collected, so the gap is visible rather than silently dropped. (Consistent with the MVP's workspace-scoped recruiter-notification model, the alert is workspace-Admin/Recruiter-scoped; per-Hiring-Manager routing is out of scope.)
- **FR-010**: A scorecard submission MUST be persisted against its `{interview occurrence, interviewer}` pair, recording who submitted (the interviewer), the candidate and interview it concerns, the structured response, and the submission timestamp.
- **FR-011**: Request and reminder email content MUST be rendered from operational templates such that every merge placeholder is substituted; a missing or empty merge value MUST NOT transmit a raw unrendered placeholder to the interviewer. (This is the operational-template render discipline for member mail; the candidate-facing template-preview "visible warning" of F21 is a distinct path and is not implied for these interviewer emails.)

**Reminder escalation**

- **FR-012**: If a feedback request is unsubmitted by the workspace-configured deadline, the system MUST send the interviewer a reminder; if still unsubmitted, it MUST send further reminders at the configured cadence, up to a bounded documented maximum. Each reminder MUST carry a distinct, machine-identifiable escalation level (so escalation order is verifiable and so "escalating urgency" is realised as distinct per-level content rather than subjective tone). A documented default applies when unconfigured — **deadline ≈ interview end + 24h; reminder levels L1/L2/L3 at deadline+0h / +24h / +48h; maximum 3 escalations** — and no reminder MUST be sent before the deadline has passed. (Because the booked interview's *end* instant is not denormalized in the data model, the implementation anchors the deadline on the booked *start* plus a configurable post-interview offset; the concrete computed instant is pinned in the plan/research and is what the boundary/DST tests assert.)
- **FR-013**: An Admin MUST be able to configure, per workspace, the feedback submission deadline and the reminder escalation cadence/maximum; the documented default (FR-012) MUST apply when unconfigured. Changing these MUST be Admin-restricted, enforced server-side, and produce an audit record (actor, old value, new value, timestamp).
- **FR-014**: Reminders MUST stop once the scorecard is submitted, the request's TTL has expired (FR-018), the interview's feedback is no longer collectible (interviewer deactivated, candidate erased, interview cancelled/rescheduled-away), or the bounded maximum escalation is reached.
- **FR-015**: The reminder task MUST run on the shared `@Scheduled` + `SchedulerCheckpoint` pattern (F00.2): idempotent across runs, recovering missed fires without sending any reminder twice. Each reminder send MUST be guarded by a per-`{request, escalation level}` atomic primitive so an overlapping fire or a mid-task restart cannot double-send.

**Token security, expiry & rate limiting**

- **FR-016**: The scorecard link MUST carry a cryptographically random token of at least 256 bits of entropy (not derived from candidate id, interviewer id, or interview id), stored only as a keyed hash at rest (the raw token is never persisted); the URL MUST contain only the token (no candidate/interviewer/interview identifier or other PII in the path or query). Token generation MUST be auditable without logging the raw token value. Because the token is write-capable (a successful guess could inject candidate-related PII), correctness MUST rest on token entropy + the single-use atomic claim (FR-019); the per-source rate limit (FR-020) is advisory only.
- **FR-017**: A scorecard token MUST grant **write-only** access to exactly one scorecard record: loading the form MUST NOT return any previously submitted content for that or any other interviewer, and **no token-routed endpoint may serve scorecard data**. The token-routed surface MUST be limited to exactly two operations — load-blank-form and submit — with the submitted-content read reachable only from the authenticated Recruiter/HM path (FR-024/FR-025); this MUST be a structural property (the token handler does not load/serialize submitted content), not merely an omission in a response body.
- **FR-018**: A scorecard token MUST expire after a configurable TTL (default 72 hours from send, consistent with other private links); a genuinely past-TTL but otherwise-valid token MUST return a distinct "expired" response with a helpful user-facing message, distinguishable from an invalid/used token, and never a 404 or 500 (but see FR-030 for the resolution precedence that prevents this becoming a state oracle).
- **FR-019**: Submission MUST be single-effective: the first valid submission records the scorecard; a subsequent submission with the same token MUST NOT create a duplicate record and MUST resolve to an idempotent "already submitted" outcome. Concurrent double-submits MUST yield at most one persisted scorecard via an atomic claim (compare-and-set on the request's open state).
- **FR-020**: The public scorecard endpoints MUST be rate-limited per source (consistent with the existing candidate-token rate limit — a bounded number of requests per minute, keyed on a hashed source identifier, never a raw IP at rest); excess requests MUST be throttled.
- **FR-021**: Deadline and escalation timing MUST be evaluated against the workspace time zone with an injectable clock, so timing is deterministic at boundaries and across a DST change (no early/late/double fire).
- **FR-030**: Token resolution MUST follow a **STATUS-before-TIME precedence** so the no-auth endpoint is never a state oracle: a token whose request has been invalidated (by candidate erasure FR-023, or interview cancel/reschedule-away FR-022), already submitted, or superseded MUST resolve to the **byte-identical invalid/used response**; an unknown/malformed token MUST resolve to that same response; only a genuinely past-TTL but otherwise-valid request MUST return the distinct "expired" message (FR-018). In particular the endpoint MUST NOT reveal "this candidate was erased" or "this interview was cancelled".

**Reschedule, cancellation & erasure interactions**

- **FR-022**: When an interview is cancelled or rescheduled away from its original time **before it occurred**, any pending feedback request for that non-occurrence MUST be invalidated (its outstanding link ceases to function per FR-030 and no further reminders are sent). Feedback already submitted for an interview that did occur MUST be retained against the original occurrence even if a later (new) occurrence is scheduled; the new occurrence is treated as a fresh interview for feedback purposes once it occurs.
- **FR-023**: When a candidate is erased (F04), all scorecards concerning that candidate and all pending feedback requests for that candidate's interviews MUST be wiped/invalidated **as an atomic part of the existing single erasure-wipe operation, with no resurrection window** (a concurrent scan or submission MUST NOT be able to re-create or complete a live request on an erased candidate): scorecard free text and any candidate-identifying content MUST be removed, the stored token hash MUST be invalidated so outstanding links cease to function (FR-030), and no further reminders MUST be sent. The erasure event remains in the append-only audit log. The authoritative guarantee is the erasure wipe plus the STATUS-before-TIME resolution (FR-030), not timing.

**Viewing, compliance & access control**

- **FR-024**: A Recruiter (and Admin) MUST be able to view, per interview, each assigned interviewer's submission status (submitted / pending) and read the content of submitted scorecards within their workspace.
- **FR-025**: Scorecard read access is restricted to **Admin and Recruiter** for the MVP, enforced server-side via method security. An Interviewer MUST NOT be able to read another interviewer's scorecard, a Read-only user MUST NOT be able to read scorecards, and a Hiring Manager MUST NOT be able to read scorecards in the MVP (HM scoped read is **deferred to F51** — see the US3 scope decision: there is no candidate→requisition→assignment data path to scope an HM on, so the capability cannot be delivered end-to-end now). The HM denial is enforced, not merely absent.
- **FR-026**: A request for a scorecard or feedback view for an identifier outside the caller's workspace MUST return an indistinguishable not-found response — never an authorization error that reveals the record exists (no existence oracle).
- **FR-027**: The system MUST expose a feedback-pending signal — per interview and per interviewer, which feedback is outstanding — that recruiters/admins can act on. This per-interview/per-interviewer status surface is what satisfies the manager-visible "compliance stats" user value of US-F32-5 / product FR-13 at MVP for the Recruiter/Admin audience. The cross-workspace **aggregate** feedback-turnaround/compliance metric, the Pipeline Health Board "feedback pending" column, and HM-scoped visibility are deferred to F50/F51 (which build the requisition↔candidate↔assignment link HM scoping needs) and consume this data.

**Privacy / logging (GDPR)**

- **FR-028**: Scorecard free-text and structured content is **personal data about the candidate** and MUST be treated as such: it MUST be encrypted at rest using the **same per-field encryption mechanism as other candidate PII** (not merely "protected"), MUST be erased on candidate erasure by clearing the field value (FR-023), and MUST NEVER be written to application logs at any level, nor returned by any token-routed endpoint (FR-017). Submission and reminder handlers MUST log only internal identifiers (candidate id, interview id, interviewer id) and value-free outcome reasons. The persisted feedback-request record MUST hold only internal identifiers, lifecycle state, reminder-level state, and the hashed token — never the raw token, the recipient address, or (other than the encrypted scorecard fields) any plaintext PII.
- **FR-029**: The interviewer's email address and the candidate's name/email MUST NOT appear in application logs or in durable diagnostic artefacts (dead-letter, audit free-text); a send or render failure MUST hand the dead-letter/audit path a **PII-free cause-class summary** (the failure's type/outcome enum only), never a raw exception message that could carry template, merge, or scorecard content. The dead-letter sanitizer is a backstop, not the primary control — the caller is responsible for passing a PII-free summary.

### Key Entities *(include if feature involves data)*

- **Feedback request**: A new persisted record representing the ask for one interviewer to score one interview occurrence. References the candidate, the interview event/booking, and the interviewer (member); carries the scorecard access token (hashed), a TTL/expiry, reminder-escalation state (level sent + timestamps), and a lifecycle status (pending → submitted / invalidated / uncollectible). De-duplicated by a uniqueness constraint over `{interview occurrence, interviewer}` (FR-003) and reminder-guarded by a per-level atomic primitive (FR-015). Stored in the `feedbackRequests` collection (index pre-declared in F00.1). Stores internal identifiers + lifecycle + hashed token only — no raw token, no recipient address.
- **Scorecard (submitted feedback)**: The interviewer's structured response — overall recommendation, optional ratings, optional free-text comment — linked to the candidate, the interview event, and the interviewer. Treated as candidate personal data (FR-028): protected at rest, erased on candidate erasure, never logged. May be the same persisted record as the feedback request (the submission populating it) or a linked record — an implementation choice; conceptually it is the captured feedback.
- **Interview occurrence (existing, F13/F10/F11)**: The booked interview — candidate, panel participants (interviewer member ids), booked start/end instant, booking reference. The trigger source (interview occurred) and the participant set for request generation. The engine reads it; it does not change it.
- **Member / interviewer (existing, F01/F02)**: The workspace member who interviewed and must submit. The request email recipient (operational member mail). Their active/deactivated status governs collectibility (FR-009).
- **Assignment (existing, F02)**: Binds a Hiring Manager to requisitions (and interviewers to interviews). Not used by F32's MVP scorecard read (HM scoped read deferred to F51 — no candidate→requisition link exists to scope on); listed because it is the future scoping source.
- **Candidate (existing, F04)**: The data-subject the scorecard concerns. The erasure source: erasing the candidate wipes their scorecards and invalidates pending requests (FR-023). Scorecard content is personal data about this entity.
- **Workspace configuration (existing, F03)**: Carries the workspace time zone and the feedback deadline / escalation cadence settings (FR-013) governing reminder timing.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: An interviewer can open a generated scorecard link with no login and submit a valid scorecard that is persisted against the correct `{interview, interviewer}` pair — verified by an end-to-end test (request generated → link followed unauthenticated → submitted → persisted → readable by recruiter).
- **SC-002**: For a panel of N interviewers on one interview, exactly N independent requests/links are created, and one interviewer's submission neither completes nor exposes another's — verified by test.
- **SC-003**: Generating feedback requests is idempotent: repeated or overlapping generation runs for the same interview occurrence produce exactly one request (and one request email) per interviewer — verified by an integration test that runs generation repeatedly.
- **SC-004**: Under an injected clock, an unsubmitted scorecard receives no reminder before its deadline; at deadline it receives reminder level L1, and continued non-submission yields L2 then L3 at the configured cadence and stops at the documented maximum (3) — verified by a test asserting the exact reminder count, the distinct per-level markers, and the ordering, and asserting zero reminders before the deadline.
- **SC-005**: Once a scorecard is submitted (or the request becomes uncollectible), no further reminders are sent for it — verified by test (reminder count asserted after submission).
- **SC-006**: A simulated mid-task restart followed by a checkpoint replay produces no duplicate reminder emails and no duplicate feedback requests — verified by integration test (realised, per the established precedent, as a checkpoint-replay / double-sweep idempotency proxy rather than a true process restart).
- **SC-007**: An expired scorecard token returns a distinct, user-facing "expired" response (not 404/500), distinguishable from an invalid/used token — verified by test.
- **SC-008**: A scorecard token is write-only and bounded: (a) the load-blank-form response contains no submitted content for this or any interviewer; (b) the only token-routed operations are load and submit (no other token-routed handler exists — asserted structurally, e.g. by a route/handler inventory check); (c) the submit response echoes no prior content — verified by test for all three.
- **SC-009**: Concurrent double-submission with the same token yields exactly one persisted scorecard — verified by a concurrent integration test (two simultaneous submissions to the same token).
- **SC-010**: The scorecard read endpoint returns scorecards to Admin and Recruiter, and refuses Interviewer (peer read), Read-only, and Hiring Manager (HM deferred to F51) — verified by a 5-role matrix contract test.
- **SC-011**: A scorecard or feedback-view request for an out-of-workspace identifier returns an indistinguishable not-found response (no existence oracle) — verified by test.
- **SC-012**: An interview cancelled or rescheduled-away before it occurred produces no feedback request, and a request already pending for such a non-occurrence is invalidated (its link stops working, no further reminders) — verified by test.
- **SC-013**: Erasing a candidate wipes all their scorecards' content and invalidates all their pending feedback requests as part of the single atomic erasure wipe (no resurrection window), outstanding links cease to function (collapsing to the indistinguishable invalid/used response per FR-030), and no further reminders are sent — verified by integration test asserting content removal, link cessation, and reminder cessation.
- **SC-014**: No scorecard content (free text or structured), no interviewer email address, and no candidate name/email appears in any application log nor in persisted dead-letter or audit records, across generation, send, submit, remind, and read flows — verified by an automated scan with PII sentinels seeded into each free-text/merge field, asserting absence in logs and in persisted artefacts, **including a forced render/send failure whose resulting dead-letter and audit records are asserted to contain only the PII-free cause-class summary** (FR-029).
- **SC-015**: A deactivated/removed interviewer receives no further reminders and the workspace's active Admin/Recruiter members are alerted that the feedback is uncollectible — verified for **both** triggers: deactivation discovered at request-generation time and at reminder time.
- **SC-016**: Reminder timing is deterministic at the deadline boundary and across a DST change in the workspace time zone (no early/late/double fire) — verified under a controlled clock.
- **SC-017**: A recruiter can see, per interview, which interviewers are still pending feedback — verified by test against seeded mixed submitted/pending state.
- **SC-018**: Every state-changing action produces the appropriate value-free audit record (actor — the token-bound interviewer id for a submission, never the raw token or PII; interview/candidate where applicable; action; timestamp): workspace feedback-setting change (FR-013), scorecard submission, request invalidation (cancel/reschedule and erasure), and token-expired-on-use — verified by audit-record assertions.
- **SC-019**: Voice-to-scorecard capture and configurable per-stage scorecard templates are absent from the MVP build — verified by confirming no such capability/endpoint exists (deferred to v1.5).
- **SC-020**: Two overlapping reminder-task fires for the same request at the same escalation level send exactly one reminder email — verified by a gated concurrent integration test asserting one send and one per-level guard record.
- **SC-021**: Requests to the public scorecard endpoints from one source beyond the configured per-minute cap are throttled (not served) — verified by test under the test-profile cap.
- **SC-022**: A scorecard submitted for an interview that occurred is retained against the original occurrence when that interview is later rescheduled, and the new occurrence generates a fresh independent request once it occurs — verified by test.
- **SC-023**: A token whose request was invalidated (by erasure or by cancel/reschedule-away), already submitted, superseded, or unknown returns the byte-identical invalid/used response (no state oracle), while a genuinely past-TTL but otherwise-valid request returns the distinct "expired" response — verified by test asserting byte-identical responses across the invalid/erased/cancelled/superseded/unknown cases.

## Assumptions

- **Recipients are interviewers (members), not candidates**: The scorecard request and its reminders go to workspace members (the interviewers) at their known member addresses via operational member mail. The candidate email-consent/erasure gate (F04/F22) governs candidate-facing mail and does **not** gate interviewer-facing operational mail. However, scorecard *content* is personal data about the candidate and is fully subject to erasure and PII-logging controls (FR-028/FR-023). This is the load-bearing distinction confirmed against the code (two email paths exist: candidate consent-gated dispatch vs. operational member mail).
- **Fixed lightweight scorecard for the MVP**: The MVP uses one fixed scorecard shape (FR-008: required four-point recommendation + optional 1–4 competency ratings + optional bounded free-text comment), designed to be completable quickly (product spec FR-22 targets "under 2 minutes"; backlog US-F32-1 says "< 5 min" — the target is "a couple of minutes", and the figure is a design goal, not a tested acceptance gate). Configurable per-stage scorecard templates are a reasonable later extension and are out of scope. Voice-to-scorecard capture is explicitly deferred to v1.5 (backlog Deferred table; product spec §11).
- **Scorecard PII storage & erasure**: Scorecard free text and structured content are encrypted at rest with the same per-field encryption-at-rest mechanism used for other candidate PII, and are cleared (field value set to empty/null, never structurally dropped) as part of the candidate's single atomic erasure wipe — so the cold-reload and erasure guarantees hold and there is no resurrection window. The erasure→feedback coupling is expected to use a narrow invalidation interface (the established lazy-dependency-break pattern) to avoid a service construction cycle. These are implementation considerations flagged for `plan.md`.
- **"Interview occurred" trigger**: A feedback request is generated after the interview's booked end/start instant has passed and the interview was not cancelled/rescheduled-away. The MVP detects this via a scheduled scan of booked interviews whose time has passed (index-backed), reusing the existing booked-interview record and its participants — no new "interview completed" event infrastructure (constitution C2/C4).
- **Token & expiry consistent with other private links**: The scorecard token follows the established private-link pattern — high-entropy random token, hashed at rest, 72-hour default TTL (configurable per workspace), per-IP rate limiting, distinct expired (410-style) vs. invalid/used (400-style) responses — reusing the candidate-style no-login security chain and rate limiter. Unlike candidate scheduling/status tokens, it is **write-only** (FR-017): it can submit but never read.
- **Reminders are idempotent via per-request state, not a candidate outbox**: Because reminders go to members (not candidates), they are guarded by reminder-level state on the feedback-request record plus the SchedulerCheckpoint pattern, rather than the candidate-keyed email outbox. Correctness rests on per-`{request, level}` atomic claims, not single-threading (single-instance scheduler topology, constitution §IV), so an overlapping fire or rolling deploy is safe.
- **Scorecard read is Admin/Recruiter only for the MVP; HM deferred to F51**: The codebase has no candidate→requisition→assignment data path (the candidate record carries no requisition reference; the requisition entity and HM assignments are F51), and no candidate-creation flow populates one — so HM "own candidates only" scoping cannot be delivered end-to-end now (constitution §II) without pulling F51 forward (§I). Consistent with the F31 precedent (HM excluded from SLA actions for the same reason), scorecard read is `hasAnyRole('ADMIN','RECRUITER')`; HM/Interviewer/Read-only are denied. When F51 builds the requisition↔candidate↔assignment link, HM scoped read can be added. Interviewers cannot read peers; the interviewer's own write path is the token, not a read.
- **Compliance stats: data here, dashboard later**: F32 exposes the per-interview/per-interviewer submission status and a basic recruiter-facing pending view. The aggregate feedback-turnaround/compliance dashboard metric and the Pipeline Health Board "feedback pending" column are owned by F50/F51 and consume this data; they are out of scope here.
- **Reuse, no new infrastructure service**: The feature reuses the booked-interview record + participants (F13/F10/F11), the role + assignment scoping (F02), the workspace settings + time zone (F03), the candidate record + erasure + audit (F04), the template library + merge renderer (F21), operational member mail + in-app recruiter notification (F01/F22), the private-token + rate-limiter + no-login chain (F13/F14/F30), and the SchedulerCheckpoint pattern (F00.2). The only net-new persistent object is the feedback-request/scorecard record in the pre-declared `feedbackRequests` collection (storage, not infrastructure — permitted).
- **Single language**: Scorecard request/reminder copy and the scorecard form labels are English for the MVP, authored from the template library with localization markers, consistent with prior candidate/member-facing features.
- **Internal viewing surface accessibility scope**: The recruiter/HM scorecard-viewing surface is an internal authenticated screen; consistent with F50/F51 precedent, the Lighthouse/WCAG candidate-facing gates apply to the public scorecard form (no-login, mobile-first) but not to the internal viewing screens.
